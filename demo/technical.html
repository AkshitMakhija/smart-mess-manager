1. Wireless Camera Stream Architecture (WebRTC P2P)

Rather than requiring students or mess staff to install a native mobile application, the system uses browser-native WebRTC (Web Real-Time Communication) orchestrated via PeerJS.

The laptop acts as the receiving monitor peer and displays a dynamic QR code encoding a secure session identifier (e.g., smm-483921). When the smartphone scans the QR code, it initializes a lightweight HTML5 client requesting rear-facing camera access (facingMode: "environment"). A direct peer-to-peer MediaStream pipeline is established using public STUN servers (Google STUN), transmitting low-latency 640×480 video wirelessly over the local network with zero external video server infrastructure.

Phone Camera Feed ──[WebRTC MediaStream]──> Laptop Browser Canvas ──[WebGL Pipeline]──> TF.js COCO-SSD

2. Edge Person Detection via TensorFlow.js (COCO-SSD)

Live video frames are processed locally on the laptop browser using TensorFlow.js running the COCO-SSD object detection model (MobileNetV2 Lite backbone).

Unlike traditional systems that transmit sensitive video feeds to third-party cloud APIs, all inference is executed on the client machine using WebGL acceleration:

  • Frames are sampled at throttled intervals (~700ms) to ensure smooth 60fps browser rendering.
  • Predictions are strictly filtered to the person class with a minimum confidence threshold of 0.40.
  • Bounding box coordinates are rendered onto an HTML5 <canvas> overlay aligned to the video feed.

3. Temporal Count Smoothing & Density Classification

Raw computer vision detections can fluctuate due to momentary optical occlusions, lighting shifts, or motion blur. To ensure dependable metrics during presentations and real-world operations, a statistical median filter is applied over a sliding window of recent frames ($W = 5$):

Raw Frame Detections: [16, 17, 19, 17, 18] Sorted Array: [16, 17, 17, 18, 19] Smoothed Median: 17 People (Displayed)

The smoothed count is mapped dynamically into standardized institutional crowd status levels:

  • 0 – 5 People: LOW (Minimal queue, immediate food service)
  • 6 – 15 People: MODERATE (Normal queue progression, seating available)
  • 16+ People: HIGH (Peak rush hour, queue waiting time > 10 mins)

4. Privacy-Preserving Architecture

Student privacy is protected by design:

  • No Persistent Video Storage: Video streams are processed in temporary RAM buffers frame-by-frame and immediately discarded.
  • No Facial Recognition: The system only detects general person silhouettes to count footfall. Individual student identities are never stored or tracked.
  • Local In-Browser Processing: No video bytes leave the laptop browser.

5. Fault-Tolerant Demonstration Design

To ensure 100% demonstration reliability during college evaluations, the architecture provides triple-redundant source options:

  1. Primary: Phone Wireless WebRTC Camera (Demonstrating true wireless IoT edge processing).
  2. Fallback 1: Integrated Laptop Webcam (One-click switch if phone Wi-Fi or mobile network drops).
  3. Fallback 2: Deterministic Simulation Mode (Generates realistic student cafeteria shifts 8 → 11 → 14 → 18... with visual canvas feedback for offline demonstration).

6. Seating Dynamics & Dietary System

The estimated footfall count directly feeds into an occupancy capacity model ($C_{total} = 250$ seats), dynamically calculating available tables ($Free = \max(0, 250 - Count)$) and zone queue waiting times. Coupled with structured nutritional schemas (calories, protein, and allergen alerts), students gain full transparency over their meal schedules and dietary health.
